Three test files under `tests/` form a flat suite run by Node's built-in `node:test` runner. `core.test.js` directly imports pure utility functions from `../core/operations/pipManager`, `../core/operations/backupManager`, and `../utils/security` and asserts their behavior against real filesystem paths. The other two files (`installPackages.test.js` and `installPackages.runCommand.test.js`) share a common mock strategy: they use `require.cache` to intercept module resolution for `../utils/processRunner`, `../core/system/envManager`, `../core/config/configManager`, `../core/config/mirrorManager`, `../core/operations/backupManager`, and `../core/system/logManager`, replacing them with in-memory `mockState` objects that record calls and expose handler callbacks. `installPackages.test.js` mocks `processRunner.runPip` so the tested `pipManager.installPackages` runs entirely in-process without spawning real processes, while `installPackages.runCommand.test.js` lets `runPip` execute its real implementation but mocks only the underlying `runCommand`, giving a hybrid integration-style verification. Both suites follow a `beforeEach` / `afterEach` lifecycle that resets `mockState`, removes cached modules via `removeMocks()`, and re-injects mocks via `injectMocks()` before each test.
